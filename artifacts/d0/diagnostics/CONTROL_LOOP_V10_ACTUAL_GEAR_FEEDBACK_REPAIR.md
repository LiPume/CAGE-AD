# Apollo—bridge—CARLA 真实挡位反馈 v10 修复记录

## 已找到什么问题

V9 的 400 帧证据证明，CARLA 车辆起步时真实挡位有 41 帧为 0，约 2.10 秒才进入 1 挡；但是 bridge 在这 41 帧仍向 Apollo 回报“前进挡”。旧回报只根据手刹和倒车开关猜挡位，没有读取 CARLA 的真实 `gear`。

这会让 Apollo 误以为车辆已经挂挡，也会让旧的“挡位一致”检查错误地显示为零问题。

## 打算怎么修

本轮只改 bridge 发给 Apollo 的底盘挡位：

- 手刹开启：回报驻车挡；
- 倒车开启或 CARLA 实际挡位小于 0：回报倒挡；
- CARLA 实际挡位等于 0：回报空挡；
- CARLA 实际挡位大于 0：回报前进挡。

明确不做以下改动：

- 不强制 CARLA 使用手动挡；
- 不主动指定 1 挡；
- 不改油门、刹车、转向或加速度滤波；
- 不改车辆质量、发动机、阻力或场景；
- 不生成数据集，不计算正式 TTC。

## 预期得到什么结果

先运行 CPU 检查，覆盖空挡、前进、倒车、驻车和连续切换。之后只运行一次 20 秒无车闭环。修复成功必须同时满足：

1. 400 帧都能读到 CARLA 真实挡位；
2. bridge 回报给 Apollo 的挡位与上述映射逐帧一致；
3. 不再出现“CARLA 是 0 挡但 Apollo 底盘说前进挡”；
4. CARLA 仍使用自动挡，最终能进入 1 挡；
5. Apollo 规划覆盖率至少 95%，速度优化失败不增加，横向偏离不超过 0.20 米，车辆前进至少 5.714 米；
6. 最终速度跟踪比例只如实报告，不把它偷偷降格或改成修复成功条件。

如果挡位反馈虽然真实，却使闭环无法运行或明显退化，本轮判为修复失败并回滚 bridge 行为；V9 的观测字段和全部失败证据仍保留。

## 测试后的结果

CPU 检查覆盖空挡、前进挡、两种倒挡表达、驻车挡及连续切换，结果全部正确。仓库离线测试为 `164 passed`。

唯一一次闭环运行是 `NO_NPC_V10_GEAR_FEEDBACK_01`，完整采集 400 帧、19.95 秒，进程正常退出，CARLA 和 bridge 已自动关闭。结果如下：

- CARLA 真实挡位：43 帧为 0，357 帧为 1，2.20 秒首次进入 1 挡；
- Apollo 底盘反馈：不再有任何“CARLA 是 0 挡但反馈为前进挡”的帧；
- 自动挡保持开启，400 帧都没有切换到手动挡；
- 按同一采样行直接比较，399 帧反馈正确，换挡瞬间有 1 帧为 CARLA 已变成 1 挡、Apollo 仍保留上一条空挡消息；
- 该帧 Apollo 底盘消息中的速度为 0.230 m/s，而同一行稍后读取的 CARLA 速度为 0.570 m/s，证明两边不是同一物理时刻，不能把它解释为 bridge 仍在伪造前进挡；
- 规划有效覆盖率 97.75%，速度优化器失败 0 次；
- 车辆前进 14.999 米，最大横向偏离约 0.051 米，基础闭环没有退化；
- 速度跟踪比例为 0.556，仍低于原定 0.70，慢车问题尚未修好。

旧总评仍显示 `FAIL`，其中一个原因是旧指标把 Apollo 命令“前进”而真实反馈“暂时空挡”算成 44 帧错误。这个旧指标现在恰好会惩罚真实反馈，不能用来证明 V10 改坏了车辆；另一个失败项是本来就尚未解决的速度跟踪。

## 修复是否成功

**反馈内容的修复成功，但 V10 的严格验收尚未全部通过。** 以前最关键的假象——CARLA 还在 0 挡、Apollo 却收到前进挡——已经从 41 帧降为 0 帧，而且闭环没有退化，因此保留这项修复，不回滚。

预先冻结的“400 帧必须逐行完全一致”只达到 399/400。唯一差异发生在自动变速箱切换的边界，现有采集把上一条 Apollo 消息和稍后的 CARLA 状态放在同一行。下一步必须先按消息时间戳对齐或在 bridge 发布点记录成对状态；在这个测量问题解决前，不再启动第二次仿真，也不调油门。
